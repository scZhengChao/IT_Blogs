## **1. 执行**\*\*`git rebase master`\*\***前的状态**

假设你的 Git 历史如下：

```text 
A --- B --- C --- D   (master)
         \
          E --- F     (feature)
```


- `A-B-C-D`是`master`分支的提交。
- `E-F`是`feature`分支的提交（基于`B`提交创建）。

***

## **2. 执行**\*\*`git rebase master`\*\***后的状态**

Git 会：

1. **找到**\*\*`feature`****分支和****`master`\*\***分支的共同祖先**（这里是`B`）。
2. **将**\*\*`feature`****分支的提交（****`E-F`）“\*\*​**摘下来”，临时保存。**
3. **将**\*\*`feature`****分支指向****`master`****的最新提交（****`D`） \*\*。
4. **将之前摘下的提交（****`E-F`****）重新应用到**\*\*`D`\*\***之后**（可能生成新的提交哈希，因为提交内容可能基于不同的代码状态）。

结果：

```markdown 
A --- B --- C --- D   (master)
                 \
                  E' --- F'  (feature)
```


- `E'`和`F'`是`E`和`F`的“重放版本”，**内容相同，但提交哈希不同（因为基于**\*\*`D`\*\***重新计算）。**
- `feature`分支现在基于`master`的最新状态，历史更线性。

## **3. 关键变化**

| 变化点                      | 说明                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------- |
| **`feature`** **分支的提交**​ | \`E\`和\`F\`被“重放”为\`E'\`和\`F'\`，提交哈希改变，但内容相同。                                                |
| **`master`** **分支的提交**​  | \*\*不会改变\*\*，仍然是\`A-B-C-D\`。                                                                |
| **合并提交**​                | \*\*不会产生合并提交\*\*（与\`git merge\`不同，\`rebase\`保持线性历史）。                                        |
| **冲突处理**​                | 如果\`E\`或\`F\`的修改与\`master\`的更新冲突，Git 会在重放时暂停，需手动解决冲突后\`git add\`+\`git rebase --continue\`。 |

## **4. 对比**\*\*`git merge`****和****`git rebase`\*\*

| 行为                       | \`git merge master\`     | \`git rebase master\` |
| ------------------------ | ------------------------ | --------------------- |
| **提交历史**​                | 产生合并提交（\`M\`），历史呈“分叉+合并” | 历史线性，无合并提交            |
| **`feature`** **分支的提交**​ | 保持原提交哈希不变                | 提交哈希改变（重放为新提交）        |
| **`master`** **分支**​     | 不变                       | 不变                    |
| **适用场景**​                | 团队协作时保留完整历史              | 本地整理提交历史后再合并          |

## **5. 后续操作建议**

- **如果**\*\*`feature`\*\***分支是本地分支**（未推送到远程）：
  - 直接`rebase`是安全的，可以保持干净的历史。
- **如果**\*\*`feature`\*\***分支已推送到远程**：
  - `rebase`会改变提交哈希，需强制推送（`git push --force`或`git push --force-with-lease`），可能影响其他协作者。
  - **更安全的做法**：在本地`rebase`后，删除远程`feature`分支并重新推送：

```markdown 
git push origin --delete feature
git push origin feature
```


## **6. 常见问题**

### **Q1:** \*\*​`rebase`****后****`feature`\*\***分支的提交看起来“消失”了？**

- 实际上是被移动到了`master`的最新提交之后，可以用`git log --graph`查看完整历史。

### **Q2:** \*\*​`rebase`\*\***过程中遇到冲突怎么办？**

1. Git 会暂停`rebase`并提示冲突文件。
2. 手动解决冲突后：

```bash 
git add <冲突文件>
git rebase --continue
```


1. 如果想放弃 rebase：

```bash 
git rebase --abort
```


## **总结**

- \*\*`git rebase master`****会让****`feature`****分支的提交“变基”到****`master`\*\***的最新状态**，历史更线性。
- \*\*`master`\*\***分支不受影响**，保持原样。
- **提交哈希会改变**（因为重新计算），已推送的分支需谨慎操作。

如果目标是保持干净的提交历史（尤其是本地分支），`rebase`是比`merge`更好的选择！ 🚀
