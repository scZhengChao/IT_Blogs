# 流式渲染和普通 SSR 渲染

好的，我们来详细对比一下 React 中使用 SSR 的流式渲染和普通 SSR 渲染的区别。

**核心概念回顾**

1. **服务端渲染：** 在服务器上将 React 组件渲染成最终的 HTML 字符串，然后将这个完整的 HTML 字符串发送给浏览器。浏览器接收到后可以立即展示内容（虽然可能还没有交互能力），然后浏览器再下载并执行 JavaScript 代码（hydration）来“激活”页面，使其具有交互性。
2. **普通 SSR：** 指的就是上面描述的标准过程：服务器等待整个应用的 React 组件树渲染完成，生成一个**完整的** HTML 字符串，然后一次性发送给客户端。
3. **流式 SSR：** 是 SSR 的一种优化形式。服务器在渲染组件树时，不是等待整个树渲染完成，而是将渲染出的 HTML **分成多个数据块**，并**边渲染边发送**这些数据块给浏览器。浏览器可以一边接收数据，一边开始解析和渲染已收到的部分 HTML。

**流式 SSR 与普通 SSR 的核心区别**

| 特性                 | 普通 SSR (渲染到字符串)                                      | 流式 SSR (渲染到流)                                                                                          |
| ------------------ | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **渲染完成时机**​        | 服务器必须等待\*\*整个应用\*\*的 HTML 完全渲染完成。                    | 服务器可以\*\*边渲染边发送\*\*，不需要等待整个应用完成。                                                                       |
| **数据传输**​          | 一次性发送一个\*\*完整的、巨大的\*\* HTML 字符串。                     | \*\*分块发送\*\*较小的 HTML 片段。                                                                               |
| **TTFB**​          | 相对较慢。用户需要等待整个 HTML 生成完毕才能收到第一个字节。                    | \*\*显著更快\*\*。服务器可以更早地发送初始 HTML 块（如 \`\<head>\` 和初始骨架屏），用户更快看到内容加载迹象。                                   |
| **FCP/LCP**​       | 需要等待完整 HTML 到达才开始解析渲染，FCP/LCP 可能较慢。                  | \*\*更快\*\*。浏览器收到第一个块（通常是骨架屏或关键内容）就能开始渲染，提升用户感知速度。                                                      |
| **内存压力**​          | 服务器需要将整个 HTML 字符串保存在内存中，对于大型应用可能导致高内存占用。             | \*\*内存占用更低\*\*。HTML 分块生成和发送，服务器不需要在内存中保存完整的巨大字符串。                                                      |
| **SEO/爬虫**​        | 完整 HTML 一次性到达，爬虫容易解析。                                | 最终也能提供完整 HTML，但分块传输对爬虫通常\*\*没有负面影响\*\*（爬虫会等待流结束）。                                                      |
| **用户体验**​          | 用户等待时间长，然后突然看到完整页面。                                  | 用户\*\*更快看到加载状态或部分内容\*\*，体验更流畅（渐进式渲染）。                                                                  |
| **实现复杂度**​         | 相对简单直接 (\`renderToString\`)。                         | 稍复杂，需要处理流 (\`renderToPipeableStream\` 或 \`renderToNodeStream\`)。                                       |
| **错误处理**​          | 渲染过程中出错，整个请求失败，用户看到白屏或错误页。                           | 可以使用 \*\*Suspense\*\* 在组件级别处理错误。即使部分组件渲染失败，服务器可以发送错误边界内容替代，其他已渲染部分仍能显示。                                |
| **与 Suspense 集成**​ | 有限。Suspense 主要用于客户端加载状态。                             | \*\*深度集成\*\*。服务器可以利用 Suspense 边界决定流的分块点。遇到 Suspense 边界（如数据加载）时，可以先发送 fallback UI，等数据准备好再发送该组件的真实 HTML。 |
| **代码分割**​          | 需配合 \`React.lazy\` 等，但首屏仍需等待所有必需代码加载 hydration 才能开始。 | 结合 Suspense 和代码分割更有效。服务器流可以包含 fallback，浏览器可以并行加载代码，代码加载完再 hydrate 对应部分。                                |

**流式 SSR 的优势详解**

1. **更快的首屏时间：**
   - **TTFB 降低：** 服务器能更快地发送第一个字节（通常是初始 HTML 骨架或关键内容），用户感觉页面开始加载得更快。
   - **渐进式渲染：** 浏览器不需要等待整个 HTML 下载完才开始渲染。它解析并渲染收到的每一个 HTML 块，用户能更快地看到内容逐步出现（尤其是首屏内容），而不是长时间的白屏后突然出现整个页面。这显著提升了 **FCP** 和 **LCP** 指标。
2. **降低服务器内存压力：**
   - 对于内容非常多的页面，生成的 HTML 字符串可能非常大。普通 SSR 需要服务器在内存中完整保存这个字符串，直到发送完毕。流式 SSR 是分块生成和发送的，服务器内存中只需要保存当前正在处理的小块数据，大大减少了内存峰值。
3. **更优雅的错误处理：**
   - 结合 React 18 的 Suspense 和错误边界，流式 SSR 可以在组件级别处理错误。如果某个组件渲染出错（比如数据获取失败），服务器可以发送该组件对应的错误边界内容（例如一个友好的错误提示组件），而**不会导致整个页面渲染失败**。其他已经成功渲染的部分仍然可以发送并显示给用户。
4. **更高效的数据获取与代码加载：**
   - **Suspense for Data Fetching：** 服务器可以识别 Suspense 边界。当遇到一个需要异步获取数据的组件时，服务器会先发送该位置的 fallback UI（如 loading 状态），然后继续渲染其他部分。等数据获取完成后，服务器再发送该组件的实际 HTML 替换 fallback。浏览器能更早地展示其他内容。
   - **代码分割：** 结合 `React.lazy` 和 Suspense，流式 SSR 可以更好地处理代码分割。服务器发送包含 fallback 的 HTML 块，浏览器在后台并行加载该组件的 JS 代码。代码加载完成后，hydration 会“激活”该组件。用户无需等待所有 JS 加载完就能看到主要内容。

**流式 SSR 的注意事项**

- **浏览器兼容性：** 流式传输依赖 HTTP/1.1 的分块传输编码或 HTTP/2，现代浏览器都支持，但需注意老旧环境。
- **实现复杂度：** 相比 `renderToString`，使用 `renderToPipeableStream` (Node.js) 或 `renderToReadableStream` (Web Streams API, 如 Cloudflare Workers, Deno) 需要处理流和事件（如 `onShellReady`, `onAllReady`, `onError`）。
- **框架支持：** 虽然可以直接使用 React 的 API，但通常借助框架（如 Next.js）来简化流式 SSR 的实现和管理。Next.js 13+ 的 App Router 默认就利用了流式渲染。
- **内容依赖：** 如果后续块的内容严重依赖于前面块的内容（比如 CSS 或 JS 的位置），需要确保流顺序正确。通常框架会处理好 `<head>` 的管理。

**总结**

- **普通 SSR (****`renderToString`****):**简单，**一次性发送完整 HTML。** 适合中小型应用或对 TTFB 要求不极致的场景。**缺点是首屏可能慢，内存压力大，错误处理不灵活。**
- **流式 SSR (****`renderToPipeableStream`****/****`renderToReadableStream`****):** 更先进，通过**分块传输实现更快的 TTFB、FCP、LCP**，降低**服务器内存压力**，并利用 Suspense 实现组件级错误处理和更优的数据加载/代码分割体验 **。是现代高性能 React SSR 应用的首选方案，尤其对于大型内容型页面或追求极致用户体验的应用。Next.js 等框架已将其作为核心特性**。

简而言之，流式 SSR 是普通 SSR 的进化版，它解决了**普通 SSR 在性能、内存和错误处理上的主要瓶颈，通过**“边生成边发送”的方式，让用户更快地看到内容，让服务器运行得更高效。
