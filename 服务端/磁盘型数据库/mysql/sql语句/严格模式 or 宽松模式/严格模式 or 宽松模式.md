# 案例

不同的数据库；如果存入的字符长度超出限制；有的是自动截断；有的就是直接报错；这是正常的吗

是的，**这种行为是完全正常的**，不同数据库对超长数据的处理策略确实存在差异，这取决于数据库的配置和设计哲学。

***

### 1. 不同数据库的默认行为对比

| 数据库             | 默认行为（严格模式）             | 是否可配置            | 典型错误或表现                                            |
| --------------- | ---------------------- | ---------------- | -------------------------------------------------- |
| **MySQL**​      | \*\*报错\*\*（Error 1406） | 可配置为截断           | \`Data too long for column\`                       |
| **PostgreSQL**​ | **报错**​                | 严格模式，不支持自动截断     | \`value too long for type character varying(255)\` |
| **SQL Server**​ | \*\*自动截断\*\*（静默丢失数据）   | 可配置为报错（通过ANSI设置） | 无错误，但数据被截断                                         |
| **Oracle**​     | **报错**​                | 严格模式             | \`ORA-12899: value too large for column\`          |
| **SQLite**​     | \*\*无长度限制\*\*（动态类型）    | 不适用              | 除非达到SQLITE\_MAX\_ LENGTH（默认10亿）                    |

### 2. 为什么会出现这种差异？

#### 设计哲学不同：

- ∙**严格型**（MySQL/PostgreSQL/Oracle）：优先保证数据完整性，宁可报错也不存入错误数据。
- ∙**宽松型**（SQL Server默认）：优先保证操作成功，但可能 silently corrupt data（静默数据损坏）。

#### 历史原因和兼容性：

- ∙不同数据库有各自的历史背景和默认配置，行为自然不同。

### 3. 如何查看和修改配置？

#### MySQL（示例）：

```sql 
-- 查看当前sql_mode（包含STRICT_TRANS_TABLES则表示严格模式）
SELECT @@sql_mode;
SELECT @@global.sql_mode; 

-- 临时禁用严格模式（允许自动截断）
SET sql_mode = '';

-- 永久修改需调整my.cnf配置文件
[mysqld]
sql_mode = ""
```


#### SQL Server：

```sql 
-- 启用ANSI警告（让超长数据报错而非截断）
SET ANSI_WARNINGS ON;
```


### 4. 最佳实践建议

1.

**永远不要依赖数据库的自动截断** &#x20;

静默截断会导致数据丢失且难以排查，应在应用层提前校验长度。
2\.

**统一使用严格模式** &#x20;

建议在MySQL等数据库中保持`STRICT_TRANS_TABLES`模式，及早发现数据问题。
