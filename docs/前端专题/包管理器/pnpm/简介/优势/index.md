### pnpm优势

`pnpm` 拥有`Yarn` 超过 `npm` 的所有附加功能：

- **安全:** 与 `yarn` 一样，`pnpm` 有一个包含所有已安装包校验和的特殊文件，用于在执行代码之前验证每个已安装包的完整性。
- **离线模式:** `pnpm` 将所有下载的包 `tarball` 保存在本地注册表镜像中。**当包在本地可用时，它从不发出请求**。使用该`--offline`参数可以完全禁止`HTTP`请求。
- **速度:** `pnpm` 不仅比 `npm` 快，而且比`yarn` 快。无论是冷缓存还是热缓存，**它都比**\*\*`yarn`快。****`yarn`**** 从缓存中复制文件，而 ****`pnpm`****只是从全局存储中链接它们 \*\*。

### 与 npm 的差别

- 与 `npm` 不同的是，`pnpm` 会校验所有的参数。 比如，`pnpm install --foo` 会执行失败，因为 `--foo` 不是 `pnpm install`的有效参数。

但是，某些依赖关系可能使用 `npm_config_` 环境变量，其中 从 `CLI` 选项中填充。 在这种情况下，你有以下选择：

- 设置明确的环境变量：`npm_config_foo=true pnpm install`
- 用 `--config.`强制使用未知选项: `pnpm install --config.foo`

# 简介

pnpm相比于npm和yarn更**节约磁盘空间并提升安装速度**。

当使用 npm 或 Yarn 时，如果你有100个项目使用了某个依赖（dependency），就会有100份该依赖的副本保存在硬盘上。 而在使用 pnpm 时，依赖会被存储在内容可寻址的存储中，所以：

1. 如果你用到了某依赖项的不同版本，那么只会将有差异的文件添加到仓库。 例如，如果某个包有100个文件，而它的新版本只改变了其中1个文件。**那么 pnpm update 时只会向存储中心额外添加1个新文件，而不会因为仅仅一个文件的改变复制整新版本包的内容**。
2. 所有文件都会存储在硬盘上的某一位置。 当软件包被被安装时，包**里的文件会硬链接到这一位置**，而不会占用额外的磁盘空间。 这允许你跨项目地共享同一版本的依赖。

因此，您在磁盘上节省了大量空间，这与项目和依赖项的数量成正比，并且安装速度要快得多！

# 特点

1、快速，pnpm 比替代方案快 2 倍

2、高效，Node\_modules 中的文件是从一个单一的可内容寻址的存储中链接过来的

3、支持monorepos，pnpm 内置支持了单体示仓库

4、严格，pnpm 默认创建了一个**非平铺的 node\_modules**，因此**代码无法访问任意包**

5、**npm  是 平铺的**；不在package.json 下的包 也可以直接导入；因为他平铺到node\_modules里面了

# 幻影依赖和分身问题

## 1. 幻影依赖（Phantom Dependencies）

### **定义**

幻影依赖是指：**代码中直接引用了某个依赖包，但这个包并没有在项目的**\*\*`package.json`\*\***中显式声明**。
由于`npm`或`yarn`的嵌套依赖结构（`node_modules`**是树形结构**），子依赖可能被“意外暴露”给父依赖，导致代码可以访问未声明的包。

### **为什么会出现？**

- 在`npm`或`yarn`的嵌套`node_modules`结构中，**子依赖会被安装在父依赖**的`node_modules`里，因此父依赖的代码可以直接访问子依赖，即使它没有在`package.json`中声明。
- 例如：
  - 你的项目依赖`A`，而`A`依赖`B`。
  - 在`npm/yarn`的嵌套结构中，`B`会出现在`A/node_modules`中，而你的项目代码可能直接`require('B')`，即使`B`没有在`package.json`中声明。

### **问题**

- **不可靠性**：如果`A`升级后不再依赖`B`，你的代码会突然报错（因为`B`被移除了）。
- **版本冲突**：不同依赖可能引入不同版本的`B`，导致运行时行为不一致。

### **pnpm 如何避免？**

`pnpm`使用 **硬链接 + 符号链接** 的方式存储依赖：

- 所有依赖都统一安装在全局存储目录（`~/.pnpm-store`），项目中的`node_modules`只包含符号链接。
- 每个包的依赖会被严格隔离在自己的`node_modules`子目录中，不会“泄漏”到父级。
- 因此，代码只能访问`package.json`中显式声明的依赖，避免了幻影依赖。

***

## 2. 分身问题（Duplicated Dependencies）

### **定义**

分身问题是指：**同一个包的不同版本被多次安装到**\*\*`node_modules`\*\***中**，导致磁盘空间浪费和潜在的版本冲突。

### **为什么会出现？**

- 在`npm`或`yarn`的嵌套`node_modules`结构中，不同依赖可能要求不同版本的同一个包，导致它们被重复安装。
- 例如：
  - 你的项目依赖`A@1.0`和`B@1.0`。
  - `A@1.0`依赖`C@2.0`，而`B@1.0`依赖`C@3.0`。
  - 在`npm/yarn`的嵌套结构中，`C@2.0`和`C@3.0`会被分别安装在`A/node_modules`和`B/node_modules`中，导致重复。

### **问题**

- **磁盘空间浪费**：同一个包的不同版本被多次存储。
- **潜在冲突**：如果代码错误地访问了错误的版本（如通过相对路径），可能导致运行时错误。

### **pnpm 如何避免？**

`pnpm`通过 **硬链接共享相同版本的包**：

- 所有依赖都存储在全局`~/.pnpm-store`中，相同版本的包只会存储一次。
- 项目中的`node_modules`只包含符号链接，指向全局存储的包。
- 不同版本的包会被分别存储，但不会重复（因为硬链接不会占用额外磁盘空间）。
- 因此，`pnpm`既避免了重复安装，又保证了版本的严格隔离。

## 对比总结

| 问题        | npm/yarn（嵌套结构）   | pnpm（硬链接 + 符号链接）  |
| --------- | ---------------- | ----------------- |
| **幻影依赖**​ | 可能发生（子依赖可能泄漏到父级） | 不会发生（严格隔离依赖）      |
| **分身问题**​ | 同一包的不同版本可能被多次安装  | 相同版本共享存储，不同版本严格隔离 |
| **磁盘空间**​ | 可能浪费（重复安装）       | 高效（硬链接共享相同版本）     |
| **依赖访问**​ | 子依赖可能被意外访问       | 只能访问显式声明的依赖       |

***

## 为什么推荐 pnpm？

1. **更安全**：避免幻影依赖，确保代码只依赖`package.json`中声明的包。
2. **更高效**：节省磁盘空间，避免重复安装。
3. **更可预测**：依赖版本严格隔离，减少运行时冲突。

如果你希望团队统一依赖管理，避免“依赖地狱”问题，`pnpm`是一个非常好的选择！ 🚀
