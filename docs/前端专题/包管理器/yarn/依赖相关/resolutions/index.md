在 `package.json` 中，`resolutions` 是一个用于 **强制锁定依赖版本** 的字段，通常由 **Yarn**（v1+）和 **PNPM** 支持，而 **NPM 原生不支持**。它的主要作用是解决依赖冲突或强制使用特定版本的子依赖项。

***

### **核心作用**

1. 1.**覆盖嵌套依赖版本** &#x20;

   即使某个间接依赖（子依赖）被其他包声明为不同版本，`resolutions` 可以强制指定统一的版本。
2. 2.**解决依赖冲突** &#x20;

   当项目依赖的两个包要求不同版本的相同子依赖时，用 `resolutions` 强制统一版本。
3. 3.**安全修复** &#x20;

   快速升级所有嵌套依赖中的某个不安全版本（如修复漏洞）。

### **语法示例（Yarn/PNPM**

```json 
{
  "resolutions": {
    "包名": "版本",
    "**/子包名": "版本"  // 递归匹配所有嵌套依赖
  }
}
```


### **常见场景**

#### 1. **强制使用特定版本**

```json 
{
  "resolutions": {
    "lodash": "4.17.21"  // 所有地方的 lodash 都强制用此版本
  }
}
```


#### 2. **修复安全漏洞**

```json 
{
  "resolutions": {
    "axios": "^1.6.2"  // 强制升级所有嵌套的 axios 到安全版本
  }
}
```


#### 3. **解决冲突**

假设 `package-a` 依赖 `lodash@^4.17.0`，而 `package-b` 依赖 `lodash@^3.0.0`，可以通过 `resolutions` 统一版本：

```json 
{
  "resolutions": {
    "lodash": "4.17.21"
  }
}
```


### **注意事项**

1. 1.**仅限 Yarn/PNPM** &#x20;

   NPM 不支持 `resolutions`，但可通过 `overrides` 实现类似功能（NPM v8+）：

```json 
{
  "overrides": {
    "lodash": "4.17.21"
  }
}
```


1. 2.**可能破坏兼容性** &#x20;

   强制覆盖版本可能导致某些依赖无法正常工作，需测试验证。
2. 3.**Yarn 的递归匹配** &#x20;

   使用 `**/包名` 可匹配所有层级的子依赖：

```json 
{
  "resolutions": {
    "**/webpack": "5.76.0"  // 所有嵌套的 webpack 都强制用此版本
  }
}
```


### **如何生效？**

- ∙**Yarn**：直接运行 `yarn install`。
- ∙**PNPM**：通过 `pnpm install` 自动应用。
- ∙**NPM**：使用 `overrides` 并运行 `npm install`。

***

### \*\*对比 ****`resolutions`**** 和 \*\***`overrides`**

| 特性     | \`resolutions\` (Yarn/PNPM) | \`overrides\` (NPM) |
| ------ | --------------------------- | ------------------- |
| 支持工具   | Yarn v1+, PNPM              | NPM v8+             |
| 递归匹配语法 | ` **/包名`                    | ` **/包名`            |
| 优先级    | 最高                          | 最高                  |

# 注意递归匹配与法的区别：

### 1.**Monorepo 中的依赖解析规则**

- ∙**工作区特性**：Monorepo 中的每个子包（`packages/*`）可能有自己的 `package.json`，但依赖通常由根目录统一管理。
- ∙**依赖提升**：默认情况下，Yarn/PNPM/NPM Workspaces 会将共用的依赖提升到根目录的 `node_modules`，避免重复安装。
- ∙**关键问题**： &#x20;

  `resolutions`/`overrides` 的生效范围是否涵盖所有子包？答案是 **取决于工具和语法**。

### 2. **`webpack": "5.76.0"`**\*\* 在 Monorepo 中的作用\*\*​

- ∙**作用范围**： &#x20;

  仅强制 **根目录的 ****`package.json`**** 中声明的 ****`webpack`**** 依赖**，或 **所有子包中直接声明的 ****`webpack`**** 依赖**（具体行为因工具而异）。
- ∙**示例**： &#x20;

  如果根目录或某个子包的 `package.json` 中有：

```json 
{
  "dependencies": {
    "webpack": "^5.0.0"
  }
}
```


此时 `"webpack": "5.76.0"` 会覆盖这些显式声明，但 ​**​不会影响子包内部嵌套的子依赖​**​（如子包依赖的某个工具包内部的 `webpack`）。

### 3. **`**/webpack": "5.76.0"`**\*\* 在 Monorepo 中的作用\*\*​

- ∙**作用范围**： &#x20;

  强制 **整个 Monorepo 中所有层级的 ****`webpack`**** 依赖**，包括：
  - ∙根目录的 `webpack`。
  - ∙所有子包直接声明的 `webpack`。
  - ∙子包内部嵌套的子依赖中的 `webpack`（如 `子包A -> 工具包B -> webpack@^4.0.0`）。
- ∙**递归匹配**： &#x20;

  `**/` 会穿透所有依赖层级，确保整个 Monorepo 内任何地方的 `webpack` 均被锁定为 `5.76.0`。

### 4. **Monorepo 中的实际场景对比**

#### 场景假设：

- ∙Monorepo 结构：

```markdown 
monorepo/
├── package.json         (根目录，使用 workspaces)
├── packages/
    ├── app/             (依赖 webpack@^5.0.0)
    ├── lib/             (依赖 tool@^1.0.0，而 tool 内部依赖 webpack@^4.0.0)
```


#### 配置效果：

1. 1\.

   **仅用 `"webpack": "5.76.0"`**：
   - ∙`app` 中的 `webpack` 升级到 `5.76.0`。
   - ∙`lib` 仍使用 `tool` 内部的 `webpack@4.x`（未覆盖嵌套依赖）。
2. 2\.

   **用 `"**/webpack": "5.76.0"`**：
   - ∙`app` 和 `lib` 中的所有 `webpack`（包括 `tool` 内部的）均强制使用 `5.76.0`。

### 5. **工具差异与注意事项**

| 工具        | 支持语法            | Monorepo 中的行为                                          |
| --------- | --------------- | ------------------------------------------------------ |
| **Yarn**​ | \`resolutions\` | ` **/` 递归覆盖所有子包和嵌套依赖，优先级最高。                            |
| **PNPM**​ | \`resolutions\` | 类似 Yarn，但依赖隔离性更强，需明确测试子包是否受影响。                         |
| **NPM**​  | \`overrides\`   | 从 v8 开始支持，` **/` 语法类似 Yarn，但需确保所有子包在 `workspaces` 列表中。 |

### 6. **Monorepo 中的最佳实践**

1. 1\.

   **统一版本（推荐）**： &#x20;

   使用 `**/` 强制全仓库版本一致，避免因嵌套依赖导致冲突：

```json 
{
  "resolutions": {
    "**/webpack": "5.76.0"
  }
}
```


1. 2\.

   **按需覆盖**： &#x20;

   若只需调整部分子包的依赖，直接在子包的 `package.json` 中声明版本，或使用 `resolutions` 精确指定包名（如 `子包名/webpack`）。
2. 3\.

   **验证依赖树**： &#x20;

   运行以下命令检查最终版本：

```bash 
yarn workspaces info    # 查看工作区结构
yarn list webpack       # 检查所有 webpack 版本
```


4\.

**风险控制**：

- ∙`**/` 可能破坏某些子包的兼容性（如依赖旧版 `webpack` 的第三方包）。
- ∙建议先在测试分支验证，再用 `--audit` 检查安全性。

### 7. **常见问题**

#### Q：为什么子包中的 `webpack` 没被覆盖？

- ∙可能原因：
  - ∙子包未正确声明在 `workspaces` 配置中。
  - ∙使用了 `npm` 但未升级到 v8+（不支持 `overrides`）。
  - ∙子包的依赖被锁定在 `yarn.lock/pnpm-lock.yaml` 中，需删除锁文件后重试。

#### Q：如何仅覆盖某个子包的依赖？

- ∙在根目录的 `resolutions` 中指定子包路径：

```json 
{
  "resolutions": {
    "packages/app/webpack": "5.76.0"
  }
}
```


### 总结

- ∙**`webpack": "5.76.0"`**：仅覆盖显式声明的依赖（根目录或子包直接依赖）。
- ∙**`**/webpack": "5.76.0"`**：强制全 Monorepo 所有层级的 `webpack`（包括嵌套子依赖）。
- ∙**优先选择**：在 Monorepo 中通常用 `**/` 确保全局一致性，但需谨慎测试兼容性。
- \*\*`**/lodash`在 npm/Yarn 的 ​`overrides`\*\***中有效**，可递归覆盖所有嵌套依赖。
- **pnpm 需显式指定路径，不支持递归通配符**。
