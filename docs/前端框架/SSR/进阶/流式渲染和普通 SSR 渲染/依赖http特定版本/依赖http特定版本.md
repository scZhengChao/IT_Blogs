# 依赖http特定版本

流式渲染的关键在于服务器能够将响应内容拆分成多个小“块”并将其逐步发送给浏览器，浏览器则能一边接收一边开始解析和渲染。这种传输机制主要依赖于：

1. **HTTP/1.1 (必须)：**
   - **核心机制：** HTTP/1.1 定义了 `Transfer-Encoding: chunked` 这个响应头。这是流式传输的基础。
   - **工作原理：** 服务器不再需要预先知道整个响应内容的长度（`Content-Length`）。它可以将响应体分成一个个大小已知的**数据块 (Chunk)** 发送。**每个块之前会发送该块的长度（16 进制数字），数据块之后发送一个长度为零的块作为结束标志。**
   - **对 SSR 的意义：** React 的 `renderToPipeableStream` / `renderToReadableStream` 正是利用了 HTTP/1.1 的分块传输编码，将**渲染生成的 HTML 分成多个数据块逐步发送给浏览器**。**流式渲染本质上只需要 HTTP/1.1 + ****`Transfer-Encoding: chunked`**** 就可以正常工作。** 现代浏览器和服务器（Node.js, 主流 Web 服务器如 Nginx/Apache）都普遍支持这个特性。
2. **HTTP/2 (强烈推荐，但不是必需)：**

- **优势：** HTTP/2 带来了**多路复用**和**首部压缩**等革命性改进。
- **对 SSR 的意义：**
  - **多路复用：** HTTP/1.1 基于分块传输，但多个请求响应之间仍然存在“队头阻塞”问题。HTTP/2 的单个 TCP 连接可以**并发承载多个请求和响应流（Streams）**。这意味着当流式 SSR 正在传输 HTML 主文档的同时，浏览器可以在同一个连接上**并行**发起关键的 CSS、JS、字体等资源的请求，服务器也通过同一个连接并行发送这些资源的响应。这大大减少了整体的加载时间。
  - **首部压缩：** HTTP 请求和响应的头部信息（Header）不再需要重复发送冗余信息，被压缩后大大减小了开销。
  - **优先级：** HTTP/2 允许为**不同的流设置优先级**。例如，可以让 HTML 内容的流（尤其是首屏内容）优先于非首屏图片的流。服务器可以根据优先级调整数据块的发送顺序（浏览器端的渲染也受此影响），进一步提升感知性能（LCP）。
- **结论：** 流式渲染本身在 HTTP/1.1 上就能运作，但其带来的最大性能**优势（尤其是在加载并行性上）需要结合 HTTP/2 才能真正发挥出来**。现代网站部署强烈建议启用 HTTP/2。

1. **HTTP/3 (未来方向，非必需)：**
   - 基于 QUIC 协议（在 UDP 上实现），主要解决了 **TCP 队头阻塞** 问题（即使某个包丢失，也不会阻塞整个连接上其他流的传输）。
   - 进一步减少延迟（尤其是高丢包网络）。
   - 其**流（Streams）** 的概念和传输效率比 HTTP/2 更好。
   - 对 SSR 传输的效率同样有益，但目前普及度还在上升阶段。流式渲染同样能受益于其高性能传输机制。

**总结流式渲染的依赖：**

- **基础依赖：** HTTP/1.1 + `Transfer-Encoding: chunked` (现代环境基本都支持)。
- **性能优化关键依赖：** **HTTP/2** (强烈推荐部署)。多路复用等特性是最大化流式渲染优势的关键。
- **未来优化：** HTTP/3 提供更低延迟和高丢包网络下的性能提升。
