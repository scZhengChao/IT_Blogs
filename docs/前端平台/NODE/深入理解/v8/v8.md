# v8

javascript  能够从浏览器端走到服务端   -------- 归根结底 是因为v

**8表现出优越的性能；碾压了目前所有的浏览器内核和引擎**

**一：内存**

    但所谓成也v8 ；败也V8；v8是浏览器的内核；而浏览器的进程开启的时候十分短暂；几乎不存在内存泄漏的问题；因为关闭浏览器就 释放了内存；且只影响当前一个客户端；

但是服务端者不一样了；一个始终开启的电脑；开启的服务器；开启的浏览器；而

\*\* v8有自己的方式来分配和管理内存的方式\*\*​

；

**同时开发者也不需要想c++工程师那样实时关注内存的分配和释放；因为javascript和java一样；有垃圾回收机制来管理内存**

\*\*    1.v8的内存限制  \*\*​

    所以： 

**node 实际上只能使用部分内存；64位大概约为1.4gb；32位大概0.7gb;即使他的物理内存有32gb；也无法将一个2gb的文件读入内存中进行字符串分析处理；这样计算机内存资源无法得到充足的使用；尽管实际上在服务端操作大内存也不是常见的需求；但是有了限制后；开发者也很不爽；总感觉是戴着镣铐跳舞；要知晓为何v8限制了内存的用量，则需要回归到v8在内存使用上的策略；**

**2.V8的对象分配**

![  ](1c5e129f7161e85ef1bfc6caffe7f567_Tx-etr14GW.png "  ")

    当我们在代码中申明变量并赋值时；

**所使用对象的内存就分配在堆中。**

如果已

**申请的堆空间内存不够分配新的对象，将继续申请堆内存，直到堆的大小超过v8的限制为止；**

v8为何要限制堆的大小：

**表层原因是因为v8最初为浏览器而设计，不太可能遇到大内存的情况；对于浏览器网页来说；v8的限制值已经绰绰有余；**

**深沉原因是v8的垃圾回收机制的限制；以1.5gb堆内存为例，v8做一次垃圾回收来说需要50ms以上，做一次非增量式的垃圾回收需要1s以上**

；

且，垃圾回收会引起js线程的暂停执行；在这样的时间花销下，应用的性能和响应能力都会直线下降。这样的情况下不仅是后端无法接受，前端浏览器也无法接受，因此在当时的情况下直接限制堆内存 是一个好的选择；  

   但是这个限制也并不是不能打开：

node在启动时可以传递--max-old-space-size 或者 --max-new-space-size来调整内存限制的大小；示例如下：

**node --max-old-space-size=1700 test.js // 单位为MB    老生代堆内存**

**node --max-new-space-size=1024 test.js // 单位为KB   新生代堆内存**

上述参数在v8初始化时生效，一旦生效就不能动态改变；可以用这个办法放宽v8默认的内存限制，避免在执行过程中稍微多用了一些内存就轻易崩溃；

\*\*    3.v8的垃圾回收机制\*\*​

**没有一种垃圾回收算法能完美适应所有的场景**

；现代的垃圾回收算法按对象的存活时间将内存的垃圾回收进行不同的分代，然后按照不同的分代施以更高效的算法；

v8的内存分代： 

**主要分为新生代和老生代。**

\*\*  新生代中的对象为存活时间较短的对象，老生代的对象为存活时间较长和常驻内存的对象：\*\* ​

![  ](86cbe4501d6a126f652c817e5226efa9_R9b1x-4T0J.png "  ")

**v8堆整体的大小就是新生代加老生代的大小；**

**适合新生代的垃圾回收算法：**

    Scavenge算法主要采用了Cheney算法：简单说就是一分为二；牺牲空间换时间；对新生代堆里存活时间短，生命周期较短的 情况非常适合；

![  ](a31bc2d0edddde80a9275f19d35b11fa_pk-RY8FKOs.png "  ")

晋升： 对象由新生代储存 转向 老生代储存 （也就是说由生命周期短的新生代转到了老生代的常驻内存；）

晋升的条件有两个：

        1.  一个是对象是否经历过Scavenge回收；

        2.一个是To空间的内存占比超过使用限制；（当要从From空间复制一个对象到To空间时，如果To空间已经使用超过了25%,这个对象直接晋升到老生代空间中；）

![  ](92faeafeb888e0d2c6efe88a97031b66_95QzS-zXC8.png "  ")

**适合老生代的垃圾回收算法：**

对于存活比重较大的老生代如果用之前的Scavenge算法有两个问题： 1.依旧有一半的空间会被浪费。2.存活对象比较多 ，复制存活对象的效率很低；
